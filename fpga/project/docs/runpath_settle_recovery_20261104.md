# 首段 result=6 与控制台中断后的处理

## 本次日志

`software/operator_logs/20261104_130107/recorded_cycle.jsonl` 中请求 12 是首段 CHECKPOSE，返回 `[12,6,106,0]`。solver=none、frames=0，说明 PS 在进入路径计算前未确认六轴全部满足停稳条件，尚未发出运动或夹爪打开动作。

之后读取的反馈已满足原到位容差：保持状态 INITIAL_HOLD、六轴使能，目标和完成帧数未变，日志 `stop_requested=false`。不能用稍后的正常反馈推断失败瞬间具体是哪一轴或哪项条件超限。

随后用户贴出的 KeyboardInterrupt 发生在 `input('ARM> ')`，意味着控制台被中断。该程序的 finally 会请求 STOP；关闭控制台和中断控制台都可能解除保持力矩。终端上的 `Terminate batch job (Y/N)?` 属于 Windows 批处理的退出确认。

## 此次电脑脚本修复

- 对明确未执行的 result=6，先检查仍为原保持状态、原目标/完成帧数未变，且反馈在原电机范围、速度保护和跟随误差范围内。
- 符合这些条件才等待，连续 3 次（间隔至少 0.1 秒）满足原位置/速度到位阈值后重新检查；最多 5 秒、最多 3 个请求。
- 已接受的运动、执行情况不明确、通信异常均不重发。几何错误等其他拒绝不重试。持续不满足停稳条件时取消后续流程，符合上述保持条件则保持原目标，且不会声称已经到位。
- 未放宽到位阈值、硬件保护或关节限位。故障、目标改变、超出安全阈值或 Ctrl+C 仍请求停止。
- STATUS 现在总是显示逐轴速度和目标；首段检查日志同时保存检查前的反馈，便于对照。
- 控制台中断会显示停止清理提示，避免以 Python 堆栈代替操作说明；中断仍不保留力矩。

此补充只修改电脑脚本。若已按上次步骤下载边界修复 ELF（SHA256 `26efd1aa0c282df839d6f17d3f5a1da99472e1240234b605d06cc83311fa02f3`），**不用再次下载或仅为本次更新重做 CAL**。更新脚本需重新启动控制台。

## 现在该做什么

1. 保持机械臂有承托；在 `Terminate batch job (Y/N)?` 输入 **Y**，结束已中断的批处理。
2. 重新打开同一目录 `00_control.cmd`，选 **5** 重连，输入 **STATUS**。此阶段不直接 RUNPATH。
3. 若为 FAULT_LOCKED，先查看保存的原因；排除问题后可显式 RECOVER，再 STATUS。RECOVER 只恢复失能待命，不使能、不移动、不续跑。
4. 只有保留的标定仍有效、期间电机电源和零点关系未改变，才可在恢复成功后显式 RESUME 保持当前位置；核对 STATUS，再显式 GOHOME 回保存的初始位。RESUME 不会自动回 HOME。
5. 如果标定无效、电机重新上电或零点关系不确定，改按总说明重新摆实物 HOME 并标定，不直接恢复历史文件。
6. 确认 INITIAL_HOLD 且停稳、路径环境合适，再执行 RUNPATH。出现有限等待信息时保持窗口开启，让本轮等待结束。若仍取消，直接输入 STATUS，保留日志，不按 Ctrl+C 代替查询。

若当前状态不清楚，先停在步骤 2，把 STATUS 输出提供出来，核对后再恢复使能。

验证只使用离线 ARM ELF、虚拟执行器和本次标定夹具，没有连接、下载或驱动实物硬件。
